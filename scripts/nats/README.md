# nats-server configs

Templates for the NATS deployment on the WireGuard mesh (`10.13.11.0/24`).

## Files

| File | Where it runs | Role |
|---|---|---|
| `core-a.conf` / `core-b.conf` / `core-c.conf` | 3 cloud hosts (10.13.11.7 / .1 / .177) | Core cluster (full mesh) + JetStream (R3 persistence) |
| `leaf.conf` | 2 desktops + Macbook | Leaf node — local clients + tunnel to core, no JetStream |
| `status.sh` | any host on the WG mesh (Macbook/desktop) | Print live cluster state via the core nodes' HTTP monitoring port (8222) |

## Install / uninstall

`install.sh` downloads nats-server via the [official installer](https://docs.nats.io/running-a-nats-service/introduction/installation)
(`curl -sf https://binaries.nats.dev/nats-io/nats-server/v2@latest | sh`), places
the config for the given role, and (on Linux) writes + enables a systemd unit.
macOS (Macbook) installs binary + config only — start manually.

```bash
# 3 cloud hosts (run on each, with its own role)
bash scripts/nats/install.sh core-a    # on 10.13.11.7
bash scripts/nats/install.sh core-b    # on 10.13.11.1
bash scripts/nats/install.sh core-c    # on 10.13.11.177

# 2 Linux desktops + Macbook
bash scripts/nats/install.sh leaf
```

- Linux: service is `nats.service` (`systemctl status nats`, `journalctl -u nats -f`).
  Core nodes get a `nats` system user + `/var/lib/nats/jetstream` data dir.
- macOS: start manually with `nats-server -c /usr/local/etc/nats/nats-server.conf`.
- Override the version selector: `NATS_REF=2.10.27 bash scripts/nats/install.sh <role>`.
- Idempotent: re-running overwrites the config and restarts the service.

Uninstall (stops service, removes binary/config/unit; **keeps** `/var/lib/nats`
data so core-node messages survive a reinstall):

```bash
bash scripts/nats/uninstall.sh
# to also delete retained JetStream data: sudo rm -rf /var/lib/nats
```

## Status

`status.sh` queries each core node's HTTP monitoring endpoint (`:8222`, no auth)
and prints `/varz` (server/cluster), `/routez` (full-mesh peers + message
counts), and `/leafz` (leafnodes connected). Run it from any host on the WG mesh:

```bash
bash scripts/nats/status.sh
# scope to a subset / override the monitoring port:
CORE_IPS="10.13.11.7 10.13.11.1" PORT=8222 bash scripts/nats/status.sh
```

This is the supported way to inspect topology. `nats server list` / `nats stream
info` return "no results … system privileges" because the core configs ship
without an `accounts {}` block (the default `$G` account is not the system
account) — see Notes. Add a system account if you need the CLI's system commands.

## After install

From any core host, create the stream once (R3, replicated to all three):

```bash
bash scripts/nats/create_stream.sh            # idempotent create/update
```

The `wxcom_msg_archive` durable consumer is auto-created by `nexo archive` on
first run. Verify the cluster: `bash scripts/nats/status.sh` (3 peers, full-mesh).
Verify the stream: `nats stream info WECOM_MSG` (replicas=3) — requires a system
account (see Notes).

## Notes

- nats-server listens on its WireGuard IP. If WG isn't up when the service
  starts, the bind fails and `Restart=on-failure` retries every 5s until WG is
  ready. If you manage WG with `wg-quick@<if>`, add it to `After=`/`Wants=` in
  the systemd unit generated by `install.sh` for a cleaner ordering.
- No `authorization {}` — WireGuard encrypts the transport. Add nsc/JWT auth if
  any client connects outside the WG mesh. Without an `accounts {}` block there
  is also no system account, so `nats server list` / `nats stream info` fail
  with "system privileges" — use `status.sh` (HTTP monitoring) instead, or add a
  system account for CLI system commands.
- `nexo drain` publishes rich events to `nexo.wecom.msg.<msgtype>`; `nexo archive`
  pulls and writes MySQL. See `scripts/schema.sql` for the table. (The bot no
  longer publishes — it writes a local outbox that drain drains.)
